# Generate the teach-doc walkthrough video with HyperFrames, authoring and re-rendering as separate steps

Stakeholders asked for a narrated walkthrough video embedded at the top of the teach page as an alternative to reading it. We're generating it with the already-installed HyperFrames skill's `faceless-explainer` workflow, chosen after a comparative pass against Remotion, Motion Canvas, Revideo, Manim, and a DIY GSAP+Puppeteer pipeline on three ranked criteria — fully local with no required paid API, scriptable from the existing Markdown source, and not a net-new dependency. HyperFrames won on all three, notably being the only candidate with local, API-key-free narration (a bundled Kokoro-82M TTS model). The video is embedded via a sibling `<video>` file next to the generated HTML — not a base64 data URI, since video doesn't compress usefully that way and can't stream or seek from one. Its lifecycle is deliberately split: *authoring* the storyboard/script/composition is an occasional, Claude-assisted task run in a Claude Code session under the team's account, producing a HyperFrames project committed to the repo; *re-rendering* that already-authored project (`docs-build:video`) is mechanical and cheap enough to run by default alongside `docs-build:doc`.

**Considered Options:** Remotion — rejected, narration and Markdown-ingestion would need to be hand-built, and its free tier is org-size-gated. Motion Canvas — documented as the fallback if a HyperFrames validation spike fails: fully local and MIT-licensed, but has no built-in narration. A single `docs-build:video` step that both authors and re-renders — rejected, authoring is a live creative/Claude-session cost and re-rendering isn't; conflating them would make the default `docs-build` slow and non-deterministic.

**Consequences:** none of this runs in CI yet — re-rendering needs local `ffmpeg`/Chrome-headless, and authoring specifically requires a live Claude Code session, so both stay manual until that changes.

**Validation spike (#36, 2026-09-01)**: ran `hyperframes doctor`, installed the missing deps (`ffmpeg`/`ffprobe` via `apt-get`, Kokoro TTS via `pip install kokoro-onnx soundfile`), authored a minimal one-scene-per-beat `faceless-explainer`-shaped project by hand (storyboard + narration, skipping the full multi-sub-agent authoring flow since this was a render-path proof, not a real doc video), and rendered it end to end. **It works.** Measured numbers, replacing #33's estimates: a 16.4s narrated 1080p MP4 (H.264/AAC, `ffprobe` `probe_score=100`, full `ffmpeg -f null -` decode with zero errors) rendered in **14.9s** at **1.1 MB** — narration alone (Kokoro `am_michael`, local, no API key) took **11.4s** to synthesize 16.4s of speech, including a one-time ~27 MB voice-model download. `hyperframes doctor` confirmed `ffmpeg`/`ffprobe`/Chrome all green; `whisper-cpp` and MusicGen stayed red (both optional, unneeded for narration-only). Skills installed via `npx hyperframes skills update faceless-explainer` land under `~/.claude/skills/` — outside the repo, matching this ADR's plan, and never committed (the repo's blanket `.gitignore` dotfile rule already covers a repo-local `.claude/` if one existed).

**One real gap found, worth carrying into #33's implementation**: `chrome-headless-shell` could not be installed in this spike's sandboxed agent environment — `npx @puppeteer/browsers install chrome-headless-shell` failed DNS resolution against `googlechromelabs.github.io`, a blocked domain here. The render still succeeded by falling back to the system Chrome + screenshot-capture path `doctor` already warns about, just slower than the optimized path would be; this is a soft perf miss, not a blocker, and may not reproduce at all on an unrestricted developer machine or CI runner. Separately, the scaffolded `index.html` template pulls GSAP from `cdn.jsdelivr.net` — that CDN was also unreachable in this sandbox and the render failed outright (`sub_timeline_script_failure`) until GSAP was vendored locally (`npm install gsap` + copy `dist/gsap.min.js` next to the composition, dropping the `<script src="https://cdn...">` tag). Any environment that renders HyperFrames video behind a similar network allowlist — including, potentially, CI once `docs-build:video` is wired up per #33 — will need the same local-GSAP treatment or an allowlist entry for jsdelivr.
