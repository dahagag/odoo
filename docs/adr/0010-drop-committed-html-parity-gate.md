# Drop the committed-HTML parity gate; rely on the docs-build unit test suite

`docs-build:parity` (`scripts/docs_build/parity_cli.py`) re-rendered every `docs/teach/*.md` entry into a temp directory on each CI run and byte-compared the result against both the committed HTML in `custom_addons/crm_methodology/static/docs/` and a `baseline_sha256` recorded per-file in `scripts/docs_build/managed_outputs.json`. The manifest hash has to be updated by hand in the same commit as any change to a managed doc or its rendered output — there is no command that does this automatically. On PR #102, a one-line URL edit to `docs/teach/sales-methodology-vs-odoo-crm.md` was correctly rebuilt into its `.html` counterpart, but `managed_outputs.json`'s `baseline_sha256` wasn't bumped alongside it, and CI failed on a manifest that was simply stale, not on any actual drift between source and served output.

ADR 0007 introduced this pipeline specifically to prevent served HTML drifting from its Markdown source (PR #32 had shipped a stale hand-authored draft). That risk was real when the pipeline was new and unproven. It no longer needs a runtime, full-repo-rebuild CI gate to manage: `scripts/docs_build/tests/` (`test_cli.py`, `test_markdown_transform.py`, `test_video_cli.py`) already exercises `build_doc`/`build_all` and the Markdown transform against fixtures on every run, and the pipeline's actual output has held up correctly across every teach-doc change to date. The parity gate's only remaining job was catching a hand-edit to committed HTML that bypasses the build entirely — a narrow case not worth a manual, per-commit hash-maintenance burden that just cost a CI run over a URL fix, and one that would recur on every future doc edit, including ones made by an AI agent (`copilot-swe-agent[bot]` has committed to these files before, and Claude Code sessions edit them too).

**Considered Options:** keep both parity sub-checks and add tooling to auto-write `baseline_sha256` on rebuild — rejected, adds a script to maintain instead of removing a maintenance burden, for a risk the unit test suite already covers at the pipeline-logic level. Drop only the committed-vs-manifest hash check and keep the generated-vs-committed rebuild-diff check — rejected in favor of the simpler cut: relying entirely on the existing unit test suite as the pipeline's correctness gate, matching how the rest of the repo's tooling is verified.

**Decision:** remove `scripts/docs_build/parity_cli.py`, `scripts/docs_build/manifest.py`, `scripts/docs_build/managed_outputs.json`, and their dedicated tests (`test_parity_cli.py`, `test_manifest.py`) as a unit — nothing else in the pipeline reads the manifest. Drop the `docs-build:parity` step from `.github/workflows/ci.yml`'s `docs-build-tests` job; that job now runs only `python3 -m unittest discover -s scripts/docs_build/tests -t .`. Remove the `docs-build:parity` row from the command table in `README.md`.

**Consequences:** a committed HTML file edited by hand (bypassing `docs-build:doc`) is no longer caught by CI — this is the accepted trade-off. Drift between `docs/teach/*.md` and its rendered output is now a code-review responsibility (the generated HTML's diff is visible in the same PR as the Markdown change) rather than an automated one. If drift becomes a recurring real problem again, the fix is a pre-commit or CI step that runs `docs-build:doc` and fails on an unstaged diff — not resurrecting a hand-maintained hash manifest.
