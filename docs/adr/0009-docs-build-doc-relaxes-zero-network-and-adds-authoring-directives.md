# `docs-build:doc` drops zero-network-requests and gets two comment directives for authoring

Issue #35 shipped `docs-build:doc`'s tracer bullet (PR #44) with an acceptance criterion that generated pages make zero network requests at view time — no CDN-linked fonts, scripts, or styles — and #46 (PR #47) then explicitly scoped audience tags, status pills, the demo badge, the sidebar TOC, the audience-filter JS, and web fonts as *out of scope*, citing that same constraint plus the lack of any Markdown convention to author them from. That constraint is now judged invalid: nothing in docs/adr/0007 (which is scoped to the static-folder publishing path, not network policy) actually requires it, and it was blocking real fidelity to the hand-authored Artifacts these docs are meant to replace. This ADR reverses it and records the follow-on decisions that unblocks.

**Self-contained now means**: no *local* images or internal links left unresolved (docs/adr/0007's actual concern) — not "no network access at all." Concretely: the Google Fonts `<link>` (Source Serif 4 / Karla / IBM Plex Mono) loads exactly as it does in the hand-authored Artifacts.

**Correction (2026-09-01)**: an earlier version of this ADR also claimed this reversal reopened CDN-loaded Mermaid diagram rendering. That was a mistake — issue #33 rejects pipeline-rendered Mermaid (parser complexity, a required headless-browser step) for reasons this network-policy reversal never addressed, at either view time or build time. That rejection stands unchanged; see #56, which tracks the actual resolution issue #33 already called for: a Claude Code session authors the two existing Mermaid sketches as finished SVG image assets, using the Mermaid syntax purely as a content sketch, not as something the pipeline renders. Issue #55 (the CDN-Mermaid ticket this mistake produced) is closed.

Reopening audience tags, status pills, the demo badge, and the interactive sidebar TOC/audience filter still needed a way to author them from plain Markdown without inventing heavy new syntax:

- **Inline components** (status pills, the demo badge, and similar inline badges) are just raw inline HTML in the real Artifacts — `<span class="pill new">New</span>` sitting inside a table cell, `<span class="demo-badge">Used in our demo</span>` sitting inside a paragraph. The transform now passes a small allowlist of inline tags through verbatim (`span`, `mark`, `sup`, `sub`, `kbd`, `br`) instead of HTML-escaping them, matching standard CommonMark's own inline-HTML behavior rather than the tracer bullet's stricter escape-everything choice. Block-level tags (`script`, `iframe`, etc.) stay escaped regardless of author intent — this is trusted-author content, not user-generated, but an allowlist still guards against a stray tag breaking page structure.
- **Document-level layout** (single-column deep-dive vs. multi-section-with-sidebar-TOC) is *not* inferable from heading count — `methodologies.html` has 8 top-level sections and still uses the narrow no-TOC layout, so it's an editorial call, not a structural one. A one-line comment directive at the top of the source file makes it explicit: `<!-- layout: main -->`, defaulting to the deep-dive layout when absent.
- **Per-section audience** (the `.tag.s/.r/.c` badges next to a heading, and the `data-tags` attribute the filter/dimming script reads off the enclosing `<section>`) uses the same directive mechanism, placed immediately above the heading it modifies: `<!-- tags: s c -->`. One parser rule — flat `key: value` inside an HTML comment — covers both the document-level and section-level case, rather than mixing a heavier YAML frontmatter block for one and plain comments for the other. An unmarked heading renders with no tags, is shown to every audience, and is never dimmed.
- **The sidebar TOC's scroll-spy highlighting and the audience-filter buttons** re-embed the original ~55-line dependency-free vanilla JS from the source Artifacts verbatim, when the multi-section layout is selected. This walks back the tracer bullet's determinism-first instinct (docs/teach/DESIGN-TOKENS.md had flagged "no embedded per-view JS state" as a goal) in favor of matching the real interactive experience stakeholders already reviewed.

**Considered and rejected**: self-hosting the three fonts as base64 `@font-face` data URIs, to keep the old zero-network guarantee while improving fidelity. Real measurements: this adds roughly 160–260 KB per generated page (depending on whether the optical-size axis is kept), with zero size advantage over the CDN — Google Fonts already serves the same Latin-subsetted, weight-specific WOFF2 files a self-hosted copy would. Once the underlying zero-network constraint was itself found invalid, this workaround had no remaining purpose.

**Consequences:** generated pages now depend on `fonts.googleapis.com` being reachable to render with correct typography at view time — a real regression from "works fully offline," accepted deliberately in exchange for visual and interactive fidelity to the reviewed Artifacts. Issue #35's "zero network requests" acceptance criterion and docs/teach/DESIGN-TOKENS.md's Fonts section are now stale against this decision and need a correcting note pointing here. The actual implementation (inline-HTML allowlist, layout/tags directives, TOC+filter script, CDN font loading) is tracked as follow-up work (#50–#54), not done by this ADR. Mermaid diagram rendering is explicitly *not* among the things this ADR unblocks — see the correction above.
